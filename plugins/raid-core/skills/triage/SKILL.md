# Triage

Move issues on the engagement's issue tracker through a small state machine of
triage roles.

If this repo treats external pull requests as a request surface (the tracker
config records whether it does), triage covers them too: **a PR is an issue
with attached code** -- same roles, same states, same machine, with a few
deltas marked "for a PR" below. Resolve a bare `#42` to an issue or PR per the
tracker config.

Every comment or issue posted to the tracker during triage **must** start with
this disclaimer:

```
> *This was generated by AI during triage.*
```

## Tracker wiring (RAID)

Read `tracker.provider` and the `tracker.labels` mapping (when present) from
`.raid/config.yaml`. The command recipes for the configured provider live in
`setup-raid`'s `references/trackers/` -- read the file at the time you need it;
nothing is copied into the repo. Skills reference the **canonical** role
(`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`,
`wontfix`), never a raw label string; convert through the mapping.

No tracker configured, or the tracker is unreachable? Report it and point the
user at `setup-raid` -- do not guess the tracker, and do not fall back to a
local one silently (setup-raid owns the `local` decision).

## Roles

Two **category** roles:

- `bug` -- something is broken
- `enhancement` -- new feature or improvement

Five **state** roles:

- `needs-triage` -- needs evaluation
- `needs-info` -- waiting on the reporter for more information
- `ready-for-agent` -- fully specified, ready for an agent working through
  `raid-mode`
- `ready-for-human` -- needs human implementation
- `wontfix` -- will not be actioned

For a PR, the same states read against the attached code: `ready-for-agent`
means a brief is attached and an agent should take the next step on the diff;
`ready-for-human` means it is ready for a human to merge.

Every triaged issue should carry exactly one category role and one state role.
If state roles conflict, flag it and ask before doing anything else.

State transitions: an unlabeled issue normally goes to `needs-triage` first;
from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or
`wontfix`. `needs-info` returns to `needs-triage` once the reporter replies.
The user can override at any time -- flag transitions that look unusual and
ask before proceeding.

## Invocation

Invoked by a human who describes what they want in natural language. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled** -- never triaged.
2. **`needs-triage`** -- evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes** --
   needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line
`[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker
config defines who counts as external) -- a colleague's in-flight PR is not
triage work. This filter is discovery-only; an explicitly named PR is always
triaged regardless of author.

Show counts and a one-line summary per item. Let the user pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels,
   author, dates; for a PR, the diff too). Parse any prior triage notes so you
   do not re-ask resolved questions. Read `GLOSSARY.md` for the domain
   vocabulary and the ADRs in the affected area (`docs/adr/`), if they exist.
   Run two checks against the codebase: (a) **redundancy** -- search for an
   existing model, notebook, or pipeline implementing the requested behavior
   by *domain concept* (using glossary terms, not the request's wording), and
   report where you looked. If found, it is an already-implemented `wontfix`
   (step 5). (b) **prior rejection** -- check `docs/adr/` for a decision that
   rejected or consciously deferred this, and surface it if so.

2. **Recommend.** Give your category and state recommendation with reasoning,
   plus a brief codebase summary relevant to the request -- including whether
   it is already implemented. Wait for direction.

3. **Verify the claim against real data.** Before any grilling, check that the
   claim holds up -- this is the same bar the build loop is held to. For a
   reported data bug, reproduce it by *running the query* against the
   source/target with read access: row counts, grain/key uniqueness, null or
   sentinel rates, the actual numbers -- not a code read alone. For a PR,
   confirm the diff does what it claims: check it out, run the relevant dbt
   build/tests or notebook validation. Report what happened: confirmed (with
   the numbers and the query that produced them), failed, or insufficient
   detail (a strong `needs-info` signal). **If you had no read access, say so
   and label the result "not validated against data"** -- the brief and the
   state recommendation carry that label, and it is never presented as
   verified. A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, run
   `grill-with-docs` (raid-core): rounds of frontier questions down the design
   tree, each settled decision written into `GLOSSARY.md`/`docs/adr/` as the
   round ends. Ask concrete examples over abstractions; never answer for the
   user.

5. **Apply the outcome:**
   - `ready-for-agent` -- post an agent brief
     ([`references/agent-brief.md`](./references/agent-brief.md)). The build
     loop picks it up from there: `raid-mode` works from tracker tickets and
     claims one before building.
   - `ready-for-human` -- same structure as an agent brief, but note why it
     cannot be delegated (judgment calls, external access, credentials,
     design decisions, manual testing against prod).
   - `needs-info` -- post triage notes (template below).
   - `wontfix` -- close, with the comment depending on *why*:
     - **Already implemented** -- the model or pipeline already exists. Point
       to where it lives; do **not** write an ADR (ADRs are for decisions,
       not built things).
     - **Rejected (bug)** -- plain explanation, then close.
     - **Rejected (enhancement)** -- if the rejection is a decision with
       consequences, record it as an ADR in `docs/adr/` (format in
       `domain-modeling`'s `references/adr-format.md`) and link it from the
       closing comment; then close. RAID keeps no separate out-of-scope store
       -- the ADR is the record a future triage checks in step 1.
   - `needs-triage` -- apply the role. Optional comment if there is partial
     progress.

## Quick state override

If the user says "move #42 to ready-for-agent", trust them and apply the role
directly. Confirm what you are about to do (role changes, comment, close),
then act. Skip grilling. If moving to `ready-for-agent` without a grilling
session, ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the
work is not lost. Questions must be specific and actionable, not "please
provide more info" -- for data issues, name the table, the date range, and the
numbers that would settle it.

## Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the
reporter has answered any outstanding questions, and present an updated
picture before continuing. Do not re-ask resolved questions.
